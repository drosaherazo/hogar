# Deploying Hogar

| Piece     | Where  | Config                                     |
| --------- | ------ | ------------------------------------------ |
| Web app   | Vercel | `apps/web/vercel.json`                     |
| Storybook | Vercel | `packages/ui/vercel.json`                  |
| API       | Render | `render.yaml` (Blueprint, two services)    |
| Database  | Neon   | connection string in Render's environment  |
| Email     | Resend | API key and sender in Render's environment |

Production lives at <https://hogar.therandomcollection.co>. A second, disposable environment, `dev`, lives at <https://dev.hogar.therandomcollection.co> (see _The `dev` environment_ and ADR 0010).

All of them have free plans. The one paid piece is Hogar's own domain (about €10–15 a year), which Resend needs to send email (see _Email_). Render's free web service sleeps after ~15 minutes without traffic, so the first request after a while takes 30–50 seconds. The web shows a wake-up screen meanwhile (ADR 0006): it polls `GET /api/health` until the API answers and only then restores the session with a single refresh, because the refresh token rotates on every use and a refresh cut off by the proxy during a cold start must never be retried blindly. Keeping the API warm with a scheduled ping would shorten those waits and is a possible future improvement.

## One origin for the browser

The browser only ever talks to the web app's domain. Vercel forwards `/api/*` to the API on Render (`rewrites` in `apps/web/vercel.json`), so the refresh cookie is first-party and `SameSite=Lax` works, just as with Vite's proxy in development. No CORS is needed.

The rewrites are chosen by host, in this order:

1. From `hogar.therandomcollection.co` only, `/api/*` goes to the production service, `https://hogar-api-m5va.onrender.com`.
2. From every other host (`dev` and every preview), `/api/*` goes to the `dev` service, `https://hogar-api-dev.onrender.com`. A preview can never read or write production data.
3. Everything else falls back to the SPA's `index.html`.

`apps/web/src/deploy/vercelRewrites.test.ts` fails if a rewrite to the production API stops being restricted to the production host, or comes after the `dev` rule. Render adds a random suffix when a service name is already taken (`hogar-api.onrender.com` belongs to someone else's app), so if a service is ever recreated, update its rewrite destination (and the test) to the new URL.

## First deploy

### 1. Database (Neon)

1. Create a project at [neon.tech](https://neon.tech): Postgres 17, region **AWS Europe Central 1 (Frankfurt)**, the same as the API.
2. In **Connect**, turn **Connection pooling off** and copy the connection string. It ends in `?sslmode=require`. Migrations need the direct connection.

### 2. API (Render)

1. In [Render](https://dashboard.render.com), **New › Blueprint**, pick the GitHub repository. Render reads `render.yaml`.
2. Fill in the variables it asks for:
   - `DATABASE_URL`: the Neon connection string.
   - `GOOGLE_CLIENT_ID`: the same Client ID as in local development.
   - `WEB_ORIGIN`: the web app's URL, exactly as the browser sees it: `https://hogar.therandomcollection.co`. If it ever changes, update this variable, the Google origin and the production rewrite's `host` in `apps/web/vercel.json`.
   - `RESEND_API_KEY` and `EMAIL_FROM`: see _Email_ below. The API refuses to start without them.

   `JWT_ACCESS_SECRET` and `EMAIL_CODE_SECRET` are generated by Render.

3. The build installs the API, bundles it with esbuild (`apps/api/build.mjs`) and applies pending migrations (`prisma migrate deploy`). Check `https://<service>.onrender.com/api/health` returns `{"status":"ok"}`.

Render deploys again on every push to `main`, once CI has passed.

### 3. Web app (Vercel)

1. In [Vercel](https://vercel.com/new), import the repository. **Root Directory:** `apps/web`. Vercel reads `apps/web/vercel.json`.
2. Environment variables:
   - `VITE_GOOGLE_CLIENT_ID`: the Client ID, for both the **Production** and **Preview** environments (`dev` builds as a preview).
   - `ENABLE_EXPERIMENTAL_COREPACK` = `1`, so Vercel uses the pnpm version in `package.json`.
3. Deploy.
4. **Settings › Domains:** add `hogar.therandomcollection.co` for production, with the DNS record Vercel shows. Edit the project's old `hogar-virid-nine.vercel.app` domain to redirect (308) to it, so nothing reaches the app under its old name (it would otherwise be routed to the `dev` API).

### 4. Storybook (Vercel)

Import the same repository again as a second project. **Root Directory:** `packages/ui`, with `ENABLE_EXPERIMENTAL_COREPACK` = `1`.

### 5. Google

In Google Cloud › **Clients** › your Web client, add `https://hogar.therandomcollection.co` to **Authorized JavaScript origins**. See `docs/setup-google-oauth.md`.

Vercel preview deployments get a different URL each time, and Google doesn't accept wildcard origins, so Google sign-in only works in production and on `dev`'s fixed URL.

## Email

The API sends sign-in codes by email (ADR 0008). Render's free web services block outbound SMTP, so it uses [Resend](https://resend.com)'s HTTP API. The free plan sends 100 emails a day; past that, people see "we couldn't send the email" (`auth.email.send_failed`), and moving to a paid plan or another provider only touches the adapter in `apps/api/src/email/mailer.ts`.

1. **Buy a domain** (about €10–15 a year at any registrar). It is the only paid dependency. Hogar uses `therandomcollection.co` for the web app (`hogar.` and `dev.hogar.`) and verifies `hogar.therandomcollection.co` in Resend for the email sender, so every sender address must end in `@hogar.therandomcollection.co`.
2. In Resend, **Domains › Add domain**, region **EU (Ireland)**. Resend lists DNS records: the **SPF** (`TXT` and `MX` on a `send` subdomain) and **DKIM** (`TXT` `resend._domainkey`) records. Add them at the registrar exactly as shown, plus a DMARC record (`TXT` `_dmarc`, value `v=DMARC1; p=none;`) so inboxes trust the mail.
3. Wait until Resend shows the domain as **Verified** (minutes to a few hours).
4. **API Keys › Create API key** with _Sending access_ for that domain only.
5. On Render, set `RESEND_API_KEY` to the key and `EMAIL_FROM` to a sender on the domain, e.g. `Hogar <hola@your-domain>`.
6. Ask for a sign-in code on the production URL and check it arrives, not in spam.

Locally nothing is sent: `pnpm db:up` starts [Mailpit](https://mailpit.axllent.org), the API sends to it through `MAILPIT_URL`, and you read the emails at <http://localhost:8025>.

## The `dev` environment

`dev` is a second, disposable copy of the app where any branch can be tried in the real deployed app before its PR is merged: on several phones, with Google and with sign-in codes, against an empty database (ADR 0010).

| Piece    | `dev`                                                                                         |
| -------- | --------------------------------------------------------------------------------------------- |
| Web app  | the same Vercel project, with `dev.hogar.therandomcollection.co` assigned to the `dev` branch |
| API      | `hogar-api-dev` in `render.yaml`, deployed from the `dev` branch                              |
| Database | the separate Neon project `hogar-dev`, empty with migrations only                             |
| Email    | Resend on the same domain, with its own API key and a sender marked `dev`                     |
| Google   | the same OAuth client, with `dev`'s origin authorized                                         |

Production data, sessions and tokens never reach `dev`: it has its own database and its own generated `JWT_ACCESS_SECRET` and `EMAIL_CODE_SECRET`. Vercel's Standard Protection stays on, so only the owner's Vercel account can open it: sign in to Vercel on every phone you test with.

### Trying a branch

```bash
git push origin <branch>:dev --force
```

Vercel and Render both deploy that commit within a few minutes, without waiting for CI, so a prototype that fails lint can still be tried; the branch's own PR runs CI. The `dev` branch is never merged, and anything on it can be overwritten at any time. Render reads `render.yaml` itself from `main`, so a change to a service's configuration (a new variable, a new command) reaches `hogar-api-dev` only once it is merged; to try one earlier, set it by hand in the service's **Environment**.

Vercel doesn't deploy `dev` again for a commit it has already deployed: pushing `main` itself, or re-pushing what `dev` already has, leaves `dev.hogar…` unchanged (or answering `DEPLOYMENT_NOT_FOUND` if it was never deployed). To deploy `main` there, push an empty commit on top of it:

```bash
git push origin "$(git commit-tree 'origin/main^{tree}' -p origin/main -m 'chore: deploy dev')":refs/heads/dev --force
```

- **Single slot.** `dev` runs one branch at a time: two branches that change the API can't be tried at once. Previews, which also reach the `dev` API, suit web-only changes.
- **Migrations.** The build applies the pushed branch's pending migrations. A branch whose migrations differ from what `dev` ran before needs a fresh database, or the API may fail on schema mismatches.
- **Shared free-plan quotas.** Both Render services draw from the workspace's 750 hours a month (both sleep when idle), and `dev` and production share Resend's 100 emails a day.
- **Previews.** Every Vercel preview of the project reaches the `dev` API too, so web-only changes of several branches can be tried in parallel (see _Previews_ below).
- **Two people, one inbox.** Sign in on a second phone with a `+` address (`you+second@gmail.com`) to try two members and real-time updates.

### Previews

Vercel builds a preview of every pushed branch (`https://hogar-git-<branch>-drosaherazos-projects.vercel.app`) and of every commit (`https://hogar-<hash>-drosaherazos-projects.vercel.app`). Their `/api/*` goes to the `dev` API, never to production.

- **Sign-in code only.** Google doesn't accept wildcard origins, so previews can't use Google sign-in. They sign in with a code: `hogar-api-dev` trusts them through `WEB_PREVIEW_ORIGIN` in `render.yaml`, `https://hogar-*-drosaherazos-projects.vercel.app`, where the `*` only matches letters, digits and dashes (ADR 0010). Production has no `WEB_PREVIEW_ORIGIN`, so it rejects every preview's origin with `request.forbidden_origin`. If the Vercel project or scope is ever renamed, update the variable. Vercel shortens a branch URL longer than 63 characters; if that preview is rejected, use its commit URL, which always fits.
- **Whatever API is on `dev`.** A preview runs its own branch's web against the API and database of whatever branch was last pushed to `dev`. That is fine for web-only changes; a branch that also changes the API must be pushed to `dev` first.
- **Behind Vercel's login.** Like `dev`, previews keep Standard Protection: sign in to Vercel on the device first.

### Setting it up

The dashboard steps only you can do are guided by a wizard; they are, in order:

1. **Neon:** a new project `hogar-dev` (Postgres 17, Frankfurt). Copy the direct connection string (pooling off).
2. **Render:** sync the Blueprint, which creates `hogar-api-dev`. Fill `DATABASE_URL` (the `hogar-dev` string), `GOOGLE_CLIENT_ID` (the same Client ID), `RESEND_API_KEY` and `EMAIL_FROM`. If Render gives the service a suffixed URL, update the `dev` rewrite in `apps/web/vercel.json` and its test.
3. **Vercel › Settings › Domains:** add `dev.hogar.therandomcollection.co` and assign it to the `dev` branch; at the registrar, add the `CNAME` Vercel shows. Check `VITE_GOOGLE_CLIENT_ID` is set for Preview, and that the old `hogar-virid-nine.vercel.app` redirects (308) to production.
4. **Resend › API Keys:** a new key named `hogar-dev` with _Sending access_ to `hogar.therandomcollection.co`, and a sender such as `Hogar dev <dev@hogar.therandomcollection.co>`.
5. **Google:** add `https://dev.hogar.therandomcollection.co` to the client's Authorized JavaScript origins.

## Client IP

The auth rate limit is per client IP. Behind proxies, Express takes the client IP from `X-Forwarded-For`, trusting as many hops as `TRUST_PROXY_HOPS` says. Too few and every user shares one proxy IP (and one limit); too many and a client can pick its own IP by sending the header. The value in `render.yaml` counts Vercel's rewrite and Render's proxy.

## Checks after a deploy

### Production

- Sign in with Google on <https://hogar.therandomcollection.co>, reload (the session is restored) and sign out.
- Sign in with a code sent by email: it arrives within seconds, in your language and not in spam.
- In the browser's dev tools, the `hogar_refresh` cookie belongs to `hogar.therandomcollection.co`, with `HttpOnly`, `Secure`, `SameSite=Lax` and `Path=/api/auth`.
- `https://hogar-virid-nine.vercel.app` redirects (308) to the production domain.

### `dev`

- `https://hogar-api-dev.onrender.com/api/health` returns `{"status":"ok"}`.
- Sign in with Google on <https://dev.hogar.therandomcollection.co>.
- Sign in with a code: the email comes from the `dev` sender.
- A new person starts without a household: the database is `hogar-dev`'s, not production's.
- On a branch preview, sign in with a code: it works, and the person and household are the ones from `dev`.
- On that preview, the `/api/*` requests in the browser's dev tools return `dev`'s data, not production's (for example, the same household as on <https://dev.hogar.therandomcollection.co>).
- Production rejects the preview's origin: `curl -i -X POST https://hogar.therandomcollection.co/api/auth/email/code -H "Origin: https://hogar-abc123-drosaherazos-projects.vercel.app"` answers `403` with `request.forbidden_origin`.
- Production still signs in as before.
